# План реализации mindfork-rs

Пошаговый план реализации, производный от [spec.md](spec.md). Организован по этапам **M0–M9** (см. [§15 спецификации](spec.md#15-этапы-реализации-и-критерии-готовности)). Каждый этап: цель → задачи (с указанием модулей/файлов FSD-структуры из [§4.2](spec.md#42-слои-сверху-вниз-зависимости-направлены-только-вниз)) → тесты → критерий готовности (DoD).

План оптимизирован для **итеративной разработки ИИ-агентами**: задачи узкие, с явными границами и проверяемым результатом; зависимости направлены вниз по слоям FSD.

---

## Соглашения и рабочий процесс

### Конвенции кода
- Rust edition 2024. Перед каждым коммитом: `cargo fmt`, `cargo clippy -- -D warnings`, `cargo test`.
- Ошибки: `anyhow::Result` в прикладных слоях (`app`, `screens`, `widgets`, `features`), `thiserror` — во внутренних библиотечных модулях (`shared/api`, `shared/storage`, `features/spellcheck`).
- Логирование — `tracing` в файл рядом с бинарником (stdout занят TUI). Никаких `println!` в рантайме.
- Каждый публичный тип/функция слоя сопровождается юнит-тестом по мере написания (не отдельным этапом).

### Дисциплина зависимостей FSD
`app → screens → widgets → features → entities → shared`. Импорт «вбок»/«вверх» запрещён. Backend-ядро (`shared/api`, `shared/storage`) доступно через трейты.

### Принцип «движок за трейтом»
Всё, что зависит от `xinfer`/HTTP, — за `EngineBackend` ([§6.1](spec.md#61-слой-движка-sharedapi)). Это даёт mock/replay в тестах и возможную замену транспорта позже. **Ни один слой выше `shared/api` не знает про HTTP/`xinfer` напрямую.**

### Ветки и коммиты
- Ветка на этап: `m0-skeleton`, `m1-inference`, … Мердж в `main` по достижении DoD этапа.
- Атомарные коммиты по задачам внутри этапа.

### Ресёрч-задачи (R)
Помечены `[R]` — требуют проверки актуального API библиотек (см. [§16.2 спецификации](spec.md#162-открытые-вопросы-уточняются-при-реализации)). Результат `[R]` фиксируется коротким ADR-комментарием в коде или в `docs/decisions/`.

## M0. Каркас

**Цель:** собирающийся бинарник; запускается и чисто закрывается пустой TUI; заложена FSD-структура и инфраструктура.

### Задачи
1. **Cargo и зависимости.** Добавить: `tokio` (features: `rt-multi-thread`, `macros`, `sync`, `process`, `time`), `ratatui`, `crossterm`, `anyhow`, `thiserror`, `tracing`, `tracing-subscriber`, `tracing-appender`, `serde`, `serde_json`, `uuid`, `chrono`. `[R]` Зафиксировать версии `cargo add`.
2. **FSD-скелет.** Создать дерево модулей из [§4.2](spec.md#42-слои-сверху-вниз-зависимости-направлены-только-вниз): `app/`, `screens/`, `widgets/`, `features/`, `entities/`, `shared/` с `mod.rs`-заглушками. Настроить видимость (`pub(crate)` по умолчанию).
3. **`shared/paths.rs`.** Определение каталога данных **рядом с бинарником** (portable); пути `settings.json`, `chats/`, `data.db`, `dictionaries/`, `personal_dictionary.txt`, лог-файл.
4. **`shared/error.rs`.** Базовые типы ошибок.
5. **Логирование.** `tracing` → файл (через `tracing-appender`), уровень из env/настроек.
6. **Single instance.** `[R]` Выбрать механизм (`single-instance` крейт / lock-файл / именованный мьютекс на Windows). Второй запуск завершается с сообщением.
7. **TUI-петля (`app/runtime.rs`).** Инициализация терминала (raw mode, alternate screen), главный цикл: `event::poll(timeout)` → обработка `Esc`/`Ctrl+C` → `draw`. **RAII-восстановление терминала** (panic hook + drop-guard, чтобы терминал не «ломался» при панике).
8. **Точка входа (`main.rs`).** Init: single-instance → tokio runtime → terminal guard → `app::run()`. Тонкая.
9. **Каркас событий (`app/events.rs`).** Объявить пустые enum `AppCommand`, `AppEvent` (наполняются на M1+).

### Тесты
- `shared/paths.rs`: корректность вычисления путей (на временном «корне»).
- Смоук: приложение стартует и завершается по `Esc`/`q` без паники (ручная проверка + по возможности тест через `ratatui::TestBackend`).

### DoD
- `cargo build` зелёный; `cargo clippy -D warnings` чист.
- Запускается пустой TUI, статус-строка «mindfork-rs», закрывается по `Esc`; терминал восстановлен (включая после паники).
- Второй экземпляр не запускается.

## M1. Инференс (минимальный сквозной чат)

**Цель:** чат с Qwen без инструментов в минимальном TUI; стриминг и отмена работают.

### Задачи
1. ✅ **API `xinfer` зафиксирован** — см. [docs/xinfer-contract.md](docs/xinfer-contract.md) (аргументы запуска, SSE-формат с `reasoning_content`/`tool_calls`, поля семплинга, EOS, эмбеддинги). **Остаётся M1-smoke** ([contract §9](docs/xinfer-contract.md)): дефолт `--port`/адрес bind, сигнал готовности (нет `/health` — поллинг `/v1/usage` или парсинг stdout), отмена через закрытие SSE, `XINFER_STREAM_AS_REASONING_CONTENT=1` на Qwen/Gemma.
2. **HTTP-зависимости.** `[R]` Выбрать клиент: `async-openai` (с расширением типов) vs `reqwest` + свои типы. Добавить `futures`/`tokio-stream`, `tokio-util` (CancellationToken).
3. **`shared/api/mod.rs` — трейт `EngineBackend`** ([§6.1](spec.md#61-слой-движка-sharedapi)): `chat_stream`, `embed` (последний — заглушка до M5). Типы `ChatRequest`, `ChatChunk`, `SamplingParams`, `ToolSchema`, `FinishReason`.
4. **`shared/api/xinfer_client.rs`** — HTTP-реализация `EngineBackend`: построение тела запроса (`messages`, `tools` пуст, семплинг), SSE-стрим → `ChatChunk::{Text,Thoughts,ToolCallDelta,Finished}`. Без строковых `stop` ([§7](spec.md#7-обработка-eos-и-стоп-токенов)).
5. **`shared/api/server.rs` — супервайзер сервера** ([§3.4](spec.md#34-управление-жизненным-циклом-сервера)): managed-запуск дочернего процесса `xinfer`, поллинг готовности, корректная остановка при выходе (drop/SIGTERM/kill на Windows), парсинг stdout/stderr в события прогресса. Режим external (только URL).
6. **Парсер «мыслей» (`shared/api/thoughts.rs`)** ([§6.5](spec.md#65-разбор-мыслей-cot)): из поля reasoning либо из `<think>…</think>` в основном потоке; корректная склейка тегов на границе чанка.
7. **Маппинг семплинга (`entities/sampling.rs` + `shared/api`)**: `SamplingConfig` → поля запроса; отбрасывание неподдерживаемых ([§8](spec.md#8-параметры-семплинга)).
8. **Минимальный оркестратор (`app/orchestrator.rs`)**: одна tokio-задача, очередь `AppCommand` (`SendMessage`, `Cancel`), запуск `chat_stream`, эмиссия `AppEvent` (`GenerationStarted/Chunk/Thoughts/Finished/Cancelled`), `CancellationToken`. Автомат `Idle/Generating/Cancelling` и `generation_id` ([§4.4](spec.md#44-потоки-выполнения-и-состояние-ui--бэкенд)).
9. **Мост tokio↔TUI (`app/runtime.rs`)**: `mpsc` команд (UI→оркестратор) и событий (оркестратор→UI); неблокирующий дренаж событий в петле рендера.
10. **Минимальный UI чата**: одно поле ввода (пока обычная строка) + лента (plain text, без markdown), статус сервера. Stop по `Esc`.

### Тесты
- `thoughts.rs`: парсинг `<think>` целиком и разрезанного по чанкам; поток без «мыслей»; поле reasoning.
- Маппинг семплинга: перенос поддерживаемых, отбрасывание неподдерживаемых, генерация случайного seed.
- Оркестратор на **mock `EngineBackend`** (поток фикстурных чанков): `SendMessage` → события в порядке; `Cancel` → `Cancelled` + частичный текст; отброс чанков с чужим `generation_id`.
- `[ignore]` интеграционный с реальным `xinfer`: загрузка маленького Qwen, стрим, отмена посреди генерации; **анти-самообрыв** на промпте, провоцирующем печать `<|im_end|>`.

### DoD
- В TUI можно отправить сообщение Qwen, увидеть стриминг ответа и «мысли»; `Esc` прерывает генерацию, частичный ответ сохраняется в ленте.
- Managed-сервер поднимается/останавливается; статус виден; ошибки запуска показываются в UI.

## M2. Доменка + хранение

**Цель:** доменные типы и персистентность (JSON + SQLite); CRUD чатов/профилей; мягкое удаление.

### Задачи
1. **`entities/`** ([§5.1](spec.md#51-основные-сущности-entities)): `MessageRole`, `Message`, `ToolCallRecord`, `Chat`, `Profile`, `CharacterNames`, `Note`, `RagDocument`, `SamplingConfig`, `MessageMetadata`, `ToolId`. Все `serde`. Поле `schema_version` в конфиге.
2. **`shared/storage/json.rs`**: репозитории `ChatRepository`, `ProfileRepository`, `ConfigRepository`. Чтение/запись `chats/{id}.json`, `profiles.json`, `settings.json`. **Атомарная запись** (write-temp + rename) + бэкап файла чата ([§5.2](spec.md#52-хранение-данных)).
3. **`shared/storage/db.rs`**: инициализация SQLite (`rusqlite`), миграции схемы, подключение `sqlite-vec`. Таблицы `notes`, `rag_documents` + виртуальная таблица векторов. `[R]` Проверить сборку/линковку `sqlite-vec` на Windows и Linux.
4. **Репозитории `NoteRepository`, `RagRepository`**: CRUD с **обязательным фильтром `profile_id`** ([§9.5](spec.md#95-изоляция-по-профилю)). kNN-поиск (sqlite-vec). Эмбеддинги пишутся, но генерируются позже (M5) — пока принимают готовый вектор.
5. **Мягкое удаление**: `is_hidden` у чатов/профилей; каскад «скрыть профиль → скрыть его чаты»; выборки с `WHERE is_hidden = 0`.
6. **`Storage` фасад (`shared/storage/mod.rs`)**: `Arc<Storage>`, внутренняя синхронизация (пул/мьютекс соединения SQLite), **никогда не вызывает наружу под локом** (инвариант).
7. **Интеграция в оркестратор**: загрузка профилей/чатов при старте; сохранение чата после хода и по дебаунс-таймеру.

### Тесты
- Serde round-trip всех сущностей; стабильность `schema_version`.
- JSON-репозитории на `tempfile`: CRUD, атомарность (симуляция прерывания), бэкап.
- SQLite на `:memory:`: CRUD заметок/RAG; **изоляция по `profile_id`** (негативные: данные чужого профиля не возвращаются); мягкое удаление и каскад; kNN на малых векторах.

### DoD
- Профили и чаты создаются, сохраняются, читаются после «перезапуска» (переоткрытие хранилища).
- Мягкое удаление работает; скрытые объекты не видны в выборках.
- Изоляция по профилю подтверждена тестами.

## M3. UI чата (полноценный)

**Цель:** полный чат-цикл в TUI: список чатов, лента с markdown/мыслями/tool-блоками, ввод `tui-textarea`, спелл-чек.

### Задачи
1. **`[R]` Выбор крейтов UI**: `tui-textarea` vs `ratatui-textarea` (совместимость с версией `ratatui`); `ratatui-markdown` (покрытие: таблицы, подсветка, сворачивание) с fallback на `tui-markdown`. Зафиксировать ADR.
2. **`widgets/message_feed.rs`**: рендер ленты, скролл, выделение сообщения/блока. **Сворачиваемые блоки** «мысли» и tool-call ([§11.3](spec.md#113-лента-сообщений)). Per-message режим Markdown.
3. **`shared/markdown.rs`**: рендер markdown в `ratatui::Text` + **unicode-аппроксимация LaTeX** (таблица подстановок: греческие буквы, стрелки, операторы, верхние/нижние индексы) ([§11.4](spec.md#114-markdown-cot-и-tool-блоки-latex)).
4. **`widgets/input_box.rs`**: `tui-textarea` (multiline), `Shift+Enter` — перенос, `Enter`/`Ctrl+Enter` — отправка (настраиваемо).
5. **`widgets/chat_list.rs`** (оверлей) ([§11.2](spec.md#112-список-чатов-оверлей)): вызов по `Ctrl+L` и кнопке; **поиск-фильтр** по названию; **две сортировки** (создание/изменение) с переключением; **переименование** (`F2`); создание (с выбором профиля — заглушка профиля до M4), клонирование, удаление; виртуализация.
6. **`widgets/status_bar.rs`**: модель, токены/контекст, профиль, состояние сервера.
7. **`screens/chat.rs`**: компоновка виджетов, роутинг фокуса, обработка горячих клавиш ([§11.7](spec.md#117-горячие-клавиши-предварительно)).
8. **`features/chat_search_sort.rs`, `features/rename_chat.rs`**: логика фильтрации/сортировки/переименования (чистые функции, тестируемы без UI).
9. **`features/spellcheck/`** ([§11.5](spec.md#115-ввод-и-редактирование-спелл-чек)):
   - `dict.rs`: загрузка `spellbook` Hunspell-словарей из `dictionaries/` (en_US, en_GB, ru_RU) в фоне; несколько активных словарей (корректно, если принято хотя бы одним); персональный словарь.
   - `segment.rs`: сегментация (`unicode-segmentation`, апострофы/дефисы).
   - `check.rs`: фоновая проверка с дебаунсом ~300 мс; `suggest`.
   - `[R]` **Отрисовка ошибок в `tui-textarea`**: прототип — выбрать механизм (стиль/собственный виджет/попап подсказок по горячей клавише). Зафиксировать решение.
10. **View-model проекция**: применение `AppEvent` к read-only состоянию UI; игнор «чужого» `generation_id`.

### Тесты
- `chat_search_sort`, `rename_chat`: чистая логика (фильтр по подстроке, оба порядка сортировки).
- `spellcheck`: `check`/`suggest` на en_US и ru_RU; сегментация (смешанный ru/en, апострофы/дефисы); несколько словарей; персональный словарь (добавление + персистентность). `[R]` Проверить качество ru_RU.
- `markdown`: подстановки LaTeX; рендер таблиц/кода (снапшот через `TestBackend`).
- View-model: применение последовательности событий, в т.ч. с неактуальным `generation_id`.

### DoD
- Полный чат-цикл в TUI: список чатов (поиск, 2 сортировки, переименование), лента (markdown, мысли, tool-блоки, скролл), ввод `tui-textarea`.
- Ошибки орфографии видны, подсказки работают (en + ru), «Добавить в словарь» сохраняется.

## M4. Профили + изоляция

**Цель:** профили с id, привязка чатов, изоляция notes/RAG, приветствие.

### Задачи
1. **`features/` профилей**: создание/редактирование/мягкое удаление `Profile`; CRUD-логика (UI-секция — на M8, здесь — модель и операции).
2. **Создание чата из профиля** ([§10](spec.md#10-профили-ии-собеседника)): копирование `default_system_message → Chat.system_message`, `character_names`, `greeting` (как первое сообщение ассистента), `default_sampling`.
3. **Выбор профиля при `Ctrl+N`** (оверлей выбора).
4. **Каскад мягкого удаления профиля** → чаты + исключение notes/RAG.
5. **Подключение изоляции**: `profile_id` пробрасывается во все обращения к notes/RAG (готовится `ToolContext` для M5).
6. **Приоритеты семплинга** ([§8.3](spec.md#83-уровни-переопределения)): `Chat.sampling_override → Profile.default_sampling → глобальный`; снимок применённого — в `Message.metadata`.

### Тесты
- Создание чата из профиля: корректное копирование полей и приветствия.
- Приоритеты семплинга (все комбинации переопределений).
- Изоляция: чат профиля A не видит notes/RAG профиля B (сквозной тест через оркестратор+storage).
- Каскад мягкого удаления профиля.

### DoD
- Чат создаётся из профиля с приветствием; редактирование профиля не меняет существующие чаты.
- Данные изолированы по `profile_id` (подтверждено тестами).

## M5. Инструменты (базовые) + клиентский agentic-loop

**Цель:** реестр инструментов, клиентский agentic-loop, заметки + RAG (+ эмбеддинги по требованию) + интроспекция.

### Задачи
1. **Контракт (`features/tools/mod.rs`)** ([§9.2](spec.md#92-контракт-инструмента)): трейт `Tool`, `ToolContext` (снимок), `ToolOutcome { result, effects }`, `ChatEffect`, `ToolRegistry`.
2. **Клиентский agentic-loop в оркестраторе** ([§6.3](spec.md#63-клиентский-agentic-loop)): обработка `finish_reason = ToolCalls`, накопление `tool_calls` из стрима, вызов инструментов, добавление assistant(tool_calls)+tool-сообщений в историю, применение `effects`, цикл до `max_tool_rounds` (8). События прогресса tool-call в UI.
3. **Сборка снимка `ToolContext`** на начало хода (`system_message`, `effective_sampling`, `last_user_message_at`, `Arc<Storage>`, `Arc<dyn EngineBackend>`).
4. **Передача схем инструментов** в `ChatRequest.tools` (только включённые в профиле ∩ глобально включённые).
5. **Эмбеддинги по требованию** ([§16.1 #4](spec.md#161-принятые-решения)): `EngineBackend::embed` — `[R]` поднять вторичный сервер эмбеддингов `xinfer` на отдельном порту, использовать, остановить; выбрать модель/размерность. Fallback — лёгкий in-process эмбеддер. Зафиксировать ADR.
6. **Инструменты:**
   - `note_save`, `note_recall` (`features/tools/notes.rs`).
   - `rag_add`, `rag_search` (`features/tools/rag.rs`): чанкинг, эмбеддинг, kNN.
   - Интроспекция (`features/tools/introspection.rs`): `get_sampling`, `set_sampling` (→ `effect`), `get_system_message`, `set_system_message` (→ `effect`), `get_last_user_message_time`.
7. **Отображение tool-блоков** в ленте (имя/аргументы/результат, сворачиваемые) — связать с `ToolCallRecord` ([§5.1](spec.md#51-основные-сущности-entities)).

### Тесты
- Каждый инструмент на mock-`Storage`/mock-движке: корректность результата; мутирующие возвращают `effects`, а не трогают `Chat`; валидность JSON-схем.
- Agentic-loop на replay-фикстуре: сообщение → tool-call → effect → tool-результат → финал; соблюдение `max_tool_rounds`; применение `set_system_message`/`set_sampling` со следующего хода.
- `[ignore]` с реальной моделью: полный agentic-цикл с тестовым инструментом.

### DoD
- Ассистент сохраняет/извлекает заметки и знания, читает/меняет system message и семплинг; tool-блоки видны в UI; лимит раундов соблюдается.

## M6. call_subagent

**Цель:** саб-агент для альтернативного мнения, с запретом вложенности и лимитами.

### Задачи
1. **`features/tools/subagent.rs`** ([§9.3.2](spec.md#932-call_subagent)): через `ctx.engine` — независимый одно-ходовый запрос (`system = system_message` от основного агента, единственное user = `message`), **без истории, без инструментов, без вложенности**.
2. **Лимиты**: токены/время на вызов; подчинение `max_tool_rounds`.
3. **Защита от рекурсии**: саб-агенту не передаётся ни один инструмент (в т.ч. `call_subagent`).
4. **UI**: показ вызова саб-агента как tool-блока (system_message + message + ответ, сворачиваемо).

### Тесты
- Саб-агент не получает инструментов и истории; лимиты применяются.
- `[ignore]` с реальной моделью: вызов возвращает строку; рекурсии/зацикливания нет.

### DoD
- Модель вызывает `call_subagent`, получает строку-результат; рекурсии нет; лимиты соблюдены.

## M7. Web + Python

**Цель:** собственный web-поиск (DuckDuckGo) и Python-исполнение, под выключателями.

### Задачи
1. **`features/tools/web.rs`** ([§9.3.1](spec.md#931-web-инструмент-собственная-реализация)): `web_search` — запрос к **DuckDuckGo** (`reqwest`), парсинг результатов (`scraper`), `[R]` выбрать эндпоинт (HTML/lite/Instant Answer); извлечение читаемого контента страниц (readability-крейт/`scraper`); опц. реранкинг через `engine.embed`. Глобальный выключатель.
2. **`features/tools/python.rs`** ([§13.2](spec.md#132-исполнение-python)): subprocess Python (путь к интерпретатору из настроек), захват stdout/stderr, **таймаут**, ограничение объёма вывода. **На Windows выключен по умолчанию** (нет OS-песочницы) + предупреждение. На Linux — таймаут + отдельный процесс.
3. **Глобальные выключатели инструментов** ([§9.4](spec.md#94-включение-инструментов)): эффективный набор = `enabled_tools ∩ глобально включённые`.

### Тесты
- `web`: парсинг фикстурного HTML-ответа DDG (без сети); извлечение контента из фикстуры.
- `python`: исполнение простого кода (если интерпретатор доступен — иначе `[ignore]`); таймаут прерывает; вывод обрезается; на Windows по умолчанию выключен.
- Глобальные выключатели корректно фильтруют инструменты.

### DoD
- Поиск в интернете и исполнение кода работают под выключателями; на Windows Python выключен по умолчанию.

## M8. Экран настроек

**Цель:** все секции настроек, профили CRUD, управление сервером/моделью.

### Задачи
1. **`screens/settings.rs`** ([§11.6](spec.md#116-экран-настроек)): навигация по секциям (боковое меню/вкладки), вход по `Ctrl+,`.
2. **Секция Модель/сервер**: режим (managed/external), путь к `xinfer`, источник модели (`--m/--w/--f`), квантизация/формат, устройства (`--d`), порт; просмотр метаданных и лог запуска. **Смена модели = перезапуск сервера.**
3. **Секция Инференс**: `max_tool_rounds`, таймауты, применимые параметры контекста/KV.
4. **Секция Семплинг**: temperature, top-k/p, min-p (если поддержан), штрафы, max_tokens, seed.
5. **Секция Профили**: CRUD, редактирование системного сообщения, имён ролей, приветствия, набора инструментов, дефолтов семплинга.
6. **Секция Инструменты**: глобальные выключатели (web, Python), модель эмбеддингов, лимиты `call_subagent`, путь к Python.
7. **Секция Интерфейс**: тема, спелл-чек (вкл/выкл, выбор словарей), раскладка клавиш.
8. **Сохранение** всех настроек в `settings.json`/`profiles.json` (через оркестратор — единственный писатель).

### Тесты
- Сериализация/десериализация настроек round-trip; применение изменений семплинга/инструментов к запросу.
- Смена модели инициирует перезапуск сервера (на mock-супервайзере).
- View-model настроек: навигация, редактирование полей.

### DoD
- Все настройки и параметры запуска `xinfer` редактируются на отдельном экране; смена модели перезапускает сервер; профили управляются через UI.

## Порядок и зависимости этапов

```
M0 ─▶ M1 ─▶ M2 ─▶ M3 ─▶ M4 ─▶ M5 ─▶ M6 ─▶ M7 ─▶ M8 ─▶ M9
                    │            │
              (UI поверх    (инструменты поверх
               domain+engine) domain+profiles+engine)
```

- **M1 и M2** независимы после M0 (можно параллелить: движок vs доменка), синхронизируются на M3.
- **M5/M6/M7** опираются на M4 (изоляция/профили) и M5-инфраструктуру agentic-loop.
- **M8** требует M4–M7 (есть что настраивать). **M9** — финальная проверка и релиз.

Каждый этап завершается мерджем в `main` по DoD; `[ignore]`-тесты с реальной моделью прогоняются вручную на M1, M5, M6, M9.
