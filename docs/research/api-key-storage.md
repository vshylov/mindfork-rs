# Исследование: ввод API-ключей в настройках и машинно-привязанное хранение в конфиге

**Статус:** развилки Р1–Р6 (§9) **приняты пользователем по рекомендациям**
(2026-07-20). **Этап 1 (ядро) — сделан** (ветка `feat/api-key-store`): формат
хранения, обе схемы шифрования, резолюция «сохранённый > env», команда
`SetApiKey` с шифрованием/персистом. **Этап 2 (UI)** — следующий. Итогом
направления станет ADR (предположительно 0008) + уточнение ADR 0004.

**Отклонения реализации от этого документа** (осознанные, зафиксированы здесь):
шифротекст кодируется **hex**, а не base64 — прецедент собственного кодека
(`features::sandbox_setup::hex_lower`) избавляет от новой зависимости, а разница
в длине строки для конфига несущественна. Резолв сохранённого ключа живёт в
`EngineManager` (`app/orchestrator/engines.rs`), а супервайзер принимает уже
расшифрованный `stored_key: Option<&str>` — так слой запуска серверов не знает
про формат хранения секретов и его тесты не требуют шифрования.

## 1. Задача

Сейчас облачные API-ключи (OpenAI / Gemini / Claude) задаются **только через
env-переменные**: конфиг хранит лишь *имя* переменной (`api_key_env`, ADR 0004
«Секреты не на диск»). Обычные пользователи слабо понимают, что такое переменные
окружения — нужен ввод ключей прямо в экране настроек и хранение в
конфигурационном файле, но **безопасно**.

Требования (постановка пользователя, 2026-07-20):

1. Ключи вводятся в окне настроек (не env).
2. Хранятся в конфигурационном файле.
3. Хранение безопасное: привязка к конкретному компьютеру (экземпляру ОС),
   шифрование машинным ключом.
4. Конфиг мигрирует между компьютерами; ключи — **пер-машинные**:

> Сценарий A/B/A: на компьютере A ввожу ключи и работаю. Переношу конфигурацию на
> компьютер B — там ключи нужно ввести заново. Возвращаюсь на A с тем же
> конфигурационным файлом — ключи там уже вводились, просто читаются из файла.

Из сценария следует ключевое свойство формата: конфиг несёт **несколько записей
ключей — по записи на машину**, каждая расшифровывается только «своей» машиной.

## 2. Текущее состояние (инвентаризация)

- **Конфиг** (`shared/config.rs`): `CloudSettings { model_name, api_key_env, url }`
  — по экземпляру на провайдера (`openai`/`gemini`/`claude`) в **каждом** из трёх
  слотов: движок ассистента (`EngineSettings`), имперсонация
  (`ImpersonationEngineSettings`), эмбеддинги (`EmbedSettings`). Плюс
  `ExternalSettings.api_key_env` (Bearer для OpenAI-совместимого прокси).
  Итого: один ключ OpenAI сегодня приходится указывать (именем env) до трёх раз.
- **Резолюция** (`app/supervisor.rs`): `resolve_api_key(api_key_env)` →
  `std::env::var` при `apply_chat`/`apply_impersonation`/`apply_embed`;
  структурная ошибка `ApiKeyError { NoName, Missing(var) }`, локализуется в
  статус-чип (`ui.err.server.no_api_key_env` / `env_missing`).
- **UI** (`screens/settings/`): поле «API-ключ (env)» (`XApiKeyEnv`/`IxApiKeyEnv`/
  `EApiKeyEnv`) — текстовое, значение = имя переменной; сеттеры в `spec.rs`
  маршрутизируют по режиму (external/облако).
- **MCP** (`config.mcp.servers[].env`) — та же модель «имена переменных-источников»
  (развилка Р8 направления плагинов). Это исследование MCP **не трогает** (env
  МCP-серверов — произвольные переменные, не 3 провайдера), но выбранный механизм
  в будущем применим и там.
- `windows-sys 0.61.2` уже target-зависимость (Job Object песочницы) с фичами
  `Win32_System_JobObjects`/`Win32_Foundation`/`Win32_Security`.
- `InputBox` **не имеет** маскированного режима (пароль-ввод) — понадобится.
- `settings.json`: атомарная запись + `.bak`, whitelist бэкапа, downgrade-guard,
  политика additive-полей `#[serde(default)]` без bump'а схемы (ADR 0006 Ф12).

## 3. Модель угроз — что защищаем, что нет (честно)

**Машинно-привязанное шифрование защищает файл, а не работающую машину.**

Защищает (и это ровно сценарий пользователя):

- копия/перенос `settings.json` (облачная синхронизация, бэкап-zip, «скинь мне
  свои настройки», флешка) **не раскрывает ключи** — вне «своей» машины это
  бесполезный шифротекст;
- бэкапы `mindfork backup` безопасно лежат где угодно (в архив едет шифротекст);
- случайное чтение конфига глазами (скриншот настроек, `cat settings.json`) ключ
  не показывает;
- на Windows (DPAPI) — и от **других пользователей той же машины**, включая
  администратора без пароля жертвы (мастер-ключ DPAPI защищён паролем логона).

НЕ защищает (фундаментально для любой схемы «приложение расшифровывает само,
без ввода пользователя»):

- от вредоносного кода, исполняющегося **под тем же пользователем на той же
  машине** — он может вызвать тот же DPAPI / вывести тот же машинный ключ. Так же
  устроены Chrome (DPAPI для паролей/cookie), Git Credential Manager и т.п. —
  это индустриальный стандарт, а не наша слабость.

Сравнение со статус-кво важно: **env-переменная не безопаснее** — она читается
любым процессом того же пользователя (`/proc/<pid>/environ`, Process Explorer) и
обычно лежит плейнтекстом в профиле шелла (`$PROFILE`, `.bashrc`). Предлагаемая
схема не слабее текущей ни в одном измерении и строго сильнее для «файла в пути».

Nuance Linux: `/etc/machine-id` world-readable → **другой локальный пользователь**,
сумевший прочитать наш `settings.json`, может вывести ключ и расшифровать.
Митигация: права на файл (см. §5, hardening `0600`) + сама модель «защищаем
файл-в-переносе». На Windows DPAPI этой слабости не имеет.

## 4. Варианты

| Вариант | Файл-переносим? | Headless Linux | Сила | Сложность |
|---|---|---|---|---|
| 1. Плейнтекст в конфиге | да | да | нет | ~0 |
| 2. OS-кейчейн (`keyring`) | **нет** (секрет в ОС-хранилище) | **нет** (нужен Secret Service/D-Bus) | высокая | средняя |
| 3. **Шифрование в конфиг машинным ключом** | **да** | да | Win: высокая; Linux: средняя | средняя |
| 4. Мастер-пароль при старте | да | да | максимальная | UX-неприемлемо |

**4.1 Плейнтекст** — отклонить: прямо противоречит постановке.

**4.2 OS-кейчейн** (крейт `keyring`: Windows Credential Manager / Secret
Service / KWallet). Сильная и «правильная» схема, но: (а) секрет живёт в
ОС-хранилище, а не в конфиг-файле — буква запроса не выполняется (сценарий A/B/A
формально работает — ключи персистят на машине, — но пользователь явно просил
файл); (б) на **headless Linux** (SSH на сервер, без DE — частая среда для
TUI-приложения) Secret Service отсутствует → нужен фолбэк → двойная сложность;
(в) новая зависимость с платформенными бэкендами (zbus и др.). Отклонить для v1;
поле `scheme` в формате (§5) оставляет дверь открытой — кейчейн можно добавить
позже как ещё одну схему без ломки формата.

**4.3 Шифрование в конфиг машинным ключом — рекомендация.**

- **Windows — DPAPI** (`CryptProtectData`/`CryptUnprotectData`, crypt32):
  системный механизм ровно этой семантики — шифрует мастер-ключом *пользователя*
  (ключами управляет ОС; привязка «пользователь + машина»; расшифровка на другой
  машине или другим пользователем невозможна). Проверено по вендоренному сорсу:
  обе функции есть в `windows-sys 0.61.2` под фичей `Win32_Security_Cryptography`
  (сама требует уже включённую `Win32_Security`; `LocalFree` для освобождения
  блоба — в уже включённой `Win32_Foundation`). Цена: +1 фича существующей
  зависимости + небольшая unsafe-обёртка (прецедент unsafe — Job Object в
  `shared/sandbox.rs`). `pOptionalEntropy` — константа приложения (не секрет, но
  отсекает generic-«DPAPI-дамперы», не знающие entropy). Известный нюанс:
  доменные roaming-профили — DPAPI-ключи пользователя едут с профилем, запись
  может расшифроваться на другой доменной машине того же пользователя; это скорее
  бонус (ключи «переехали» вместе с профилем), не дефект.
- **Linux — HKDF(machine-id) + ChaCha20-Poly1305**: ключ =
  `HKDF-SHA256(ikm = содержимое /etc/machine-id, salt = константа приложения,
  info = "mindfork-rs api-key v1" + имя пользователя)`; шифрование — AEAD
  ChaCha20-Poly1305, случайный 12-байтовый nonce префиксом к шифротексту.
  `/etc/machine-id` — стабильный идентификатор экземпляра ОС (systemd);
  документация systemd сама предписывает не использовать его сырым, а выводить
  app-specific ключ через HKDF (паттерн `sd_id128_get_machine_app_specific`) —
  делаем ровно это. Имя пользователя в `info` даёт per-user привязку (зеркало
  DPAPI-семантики). Фолбэк ikm: `/var/lib/dbus/machine-id`; нет обоих
  (не-systemd экзотика) → схема недоступна, статус-чип объясняет, env-путь
  остаётся. Клонированный образ ВМ (одинаковый machine-id) расшифрует запись на
  обеих копиях — это семантика machine-id, приемлемо.

**4.4 Мастер-пароль** — единственный вариант, честно защищающий от локальной
малвари, но спрашивать пароль при каждом запуске чат-приложения — неприемлемый
UX для целевого «обычного пользователя». Вне объёма (не обещаем и на будущее).

## 5. Дизайн (вариант 4.3)

### Формат в `settings.json`

```jsonc
"api_keys": [
  {
    "label": "DESKTOP-AB12 · 2026-07-20",   // только для человека: имя компьютера + дата
    "scheme": "dpapi",                       // "dpapi" | "machine-key-v1"
    "check": "hex…",                         // шифротекст константы — проба «наша ли запись»
    "keys": { "openai": "hex…", "claude": "hex…" }  // провайдер → шифротекст ключа
  },
  { "label": "laptop · 2026-07-21", "scheme": "machine-key-v1", "check": "…", "keys": { … } }
]
```

- Поле `AppConfig.api_keys: Vec<ApiKeyEntry>`, `#[serde(default)]` +
  `skip_serializing_if = "Vec::is_empty"` → **additive, без миграции и bump'а
  схемы** (политика ADR 0006 Ф12); старые конфиги читаются как есть.
- **Идентификация записи — проба расшифровкой** поля `check` (шифротекст
  фиксированной константы): при загрузке перебираем записи, «наша» = та, чей
  `check` расшифровался (DPAPI вернул успех / AEAD-аутентификация сошлась).
  Явного machine-id в файле **нет** — не светим идентификатор машины в
  переносимом конфиге (privacy-бонус), а Windows-пути понятие machine-id вообще
  не нужно. `label` — интернируемая строка для человека (`COMPUTERNAME` /
  `/etc/hostname`, фолбэк `"?"`), в логике не участвует.
- Семантика записи: ввод ключа → «наша» запись есть — заменить в ней; нет —
  создать. Удаление ключа (пустой коммит) → убрать из записи; опустевшая запись
  удаляется. Чужие записи никогда не трогаются (они «оживут» на своих машинах).

### Провайдер-центричное хранение

Ключи хранятся **по провайдерам** (`openai`/`gemini`/`claude`), не по слотам
(чат/имперсонация/эмбеддинги): один ключ OpenAI обслуживает все три слота. Это
снимает сегодняшнее «указать env-имя трижды». External-прокси (произвольный URL,
power-user фича) остаётся env-only (Р4).

### Резолюция ключа

`resolve_api_key(provider, stored, api_key_env)`, порядок:

1. **сохранённый ключ этой машины** (расшифрованный из `api_keys`);
2. фолбэк — env-переменная по `api_key_env` (как сейчас).

Сохранённый приоритетнее: он введён явным действием в приложении, а целевой
пользователь env не видит вовсе. env остаётся для CI, power users и систем без
machine-id. Расшифровка — при `apply_*` (как сегодняшний `env::var`), не
пер-запрос.

### Раскладка по коду

- **`shared/secrets.rs`** (новый; `thiserror` по конвенции `shared`): чистое ядро
  `encrypt_with_key`/`decrypt_with_key`/`derive_key(ikm, user)` — тестируемо на
  любой ОС инъекцией ikm; платформенное — `machine_ikm()` (Linux) и
  DPAPI-обёртка (Windows) за `#[cfg]`. Публичная поверхность:
  `encrypt(plaintext) -> ApiKeyCipher`, `try_decrypt(entry) -> Option<String>`,
  `probe(entry) -> bool` (для `check`).
- **Плейнтекст живёт только в пути ввода**: `SettingsIntent::SetApiKey
  { provider, key }` → `AppCommand::SetApiKey` → оркестратор шифрует
  (`shared::secrets`) и кладёт в `config.api_keys` → `save_config` → пометка в
  `RestartQueue` (пере-подъём затронутых серверов с дебаунсом, как правки
  движка). В UI-снимок конфига ни плейнтекст, ни шифротекст не попадают: UI
  получает лишь флаги «настроен на этой машине» (расширение `AppEvent::Settings`,
  прецеденты `language_locked`, `McpSnapshot`).
- **Round-trip защита**: `handle_update_config` восстанавливает `api_keys` из
  прежнего конфига (UI-копия может быть устаревшей и не несёт ключей вовсе) —
  прецеденты `last_active_chat` и наследование MCP-пинов.
- **Супервайзер**: `apply_*` получают уже разрешённые ключи (или срез
  `api_keys` + вызов `shared::secrets`) — деталь этапа реализации; статус-чип
  получает новую причину «ключ не задан: введите в настройках или задайте
  env-переменную» (обновлённые `ui.err.server.*`).
- **Дисциплина**: ключи не логируются (существующее правило — тело ошибок клиентов
  уже обрезается; добавить внимание в ревью), UI никогда не отображает сохранённый
  ключ (см. §6).

### Hardening (опционально, дёшево)

- На Unix выставлять `0600` на `settings.json` при атомарной записи (сейчас права
  умолчания). Windows ACL не трогаем (профиль пользователя и так закрыт).
- `zeroize` для плейнтекста в памяти — **не делаем**: ключ всё равно живёт в
  `String` заголовков HTTP-клиентов весь сеанс; церемония не окупается.

## 6. UI (экран настроек)

- В облачных подсекциях (Ассистент / Имперсонация / Эмбеддинги при режиме
  openai/gemini/claude) — новое поле **«API-ключ»** над существующим
  «API-ключ (env)»:
  - значение-статус: «настроен (этот компьютер)» / «не настроен» — **сам ключ не
    показывается никогда**; Enter открывает **пустой** маскированный редактор
    (редактирование = ввод заново; восстановить секрет через UI нельзя);
  - коммит непустого → `SetApiKey`; коммит пустого → удалить ключ этой машины;
    `Del` на поле — тоже удаление (зеркало `Del`-сброса);
  - описание поля поясняет: ключ общий для чата/имперсонации/эмбеддингов этого
    провайдера, хранится зашифрованным и привязан к этому компьютеру; на другом
    компьютере вводится заново.
- **`InputBox` — режим `mask`** (новый, по образцу `single_line`): рендер `•` на
  символ, спелл-чек и подчёркивания выключены, `Ctrl+C`/`Ctrl+X` (копирование
  содержимого) — no-op, вставка (`Ctrl+V`) работает. Ширина `•` = 1 — курсор и
  hscroll не требуют правок.
- «API-ключ (env)» остаётся ниже как поле для power users (описание — «фолбэк,
  если ключ не введён»).
- Чужие записи (`api_keys` других машин) в v1 в UI не показываются и не
  редактируются (Р6); поиск `/` подхватит новое поле автоматически.
- i18n: новые ключи `ui.settings.field.api_key`, `ui.settings.desc.api_key`,
  статусные значения, обновлённые `ui.err.server.*` (ru+en; гейты parity
  накроют автоматически).

## 7. Зависимости и лицензии

| Что | Зачем | Природа |
|---|---|---|
| `chacha20poly1305` (RustCrypto) | AEAD Linux-схемы | чистый Rust, MIT/Apache-2.0 (в allowlist deny.toml) |
| `hkdf` (RustCrypto) | вывод ключа из machine-id | чистый Rust, крошечный; `sha2` уже прямая зависимость |
| `windows-sys` | DPAPI | **уже есть**; +фича `Win32_Security_Cryptography` |

Новых C-зависимостей нет; `cargo deny` останется зелёным (лицензии в allowlist).

## 8. Тестирование

- **Юниты** (любая ОС): round-trip `encrypt`/`decrypt` Linux-схемы с
  инъектированным ikm; расшифровка чужим ключом → отказ (AEAD); `probe` по
  `check`; serde-формат (default/skip, неизвестная `scheme` не валит чтение —
  запись просто «не наша»); резолюция «сохранённый > env»; round-trip защита
  `handle_update_config`; **персист без плейнтекста** (после `SetApiKey`
  сериализованный конфиг не содержит подстроку ключа); UI (поле-статус, маска,
  пустой редактор при настроенном ключе, интент).
- **`#[cfg(windows)]`**: DPAPI round-trip на живой машине CI/dev (Windows-джоб CI
  уже есть).
- **Живой прогон**: движок по существу не затронут (тот же ключ уходит в тот же
  заголовок) — достаточно ручного смоука: ввести реальный ключ в настройках →
  облачный чат работает; скопировать `settings.json` на другую машину (или тест с
  подменённым ikm) → статус «не настроен», ввод заново → работа; возврат на
  первую машину → работает без ввода. Существующие облачные `#[ignore]`-смоуки
  (`MINDFORK_ANTHROPIC_KEY` и др.) не трогаются — они про клиентов.

## 9. Развилки (на подтверждение)

- **Р1. Схема хранения.** (а) **шифрование в конфиг машинным ключом — рекомендация**
  (буква запроса, headless-совместимо, сценарий A/B/A «из коробки»);
  (б) OS-кейчейн `keyring` — отклонить для v1 (секрет не в файле; headless Linux);
  (в) плейнтекст — отклонить. Поле `scheme` оставляет (б) как будущую добавку.
- **Р2. Windows-механизм.** (а) **DPAPI — рекомендация** (родной, сильнее:
  защищает и от других пользователей машины; +1 фича уже имеющейся зависимости);
  (б) единый путь HKDF(MachineGuid) на обеих ОС — проще на ~50 строк, но слабее
  и всё равно требует чтения реестра.
- **Р3. Приоритет резолюции.** (а) **сохранённый ключ > env — рекомендация**
  (явное действие в приложении; целевой пользователь env не видит);
  (б) env > сохранённый (конвенция 12-factor, но молчаливо переопределяет UI).
- **Р4. Охват v1.** (а) **три облачных провайдера, провайдер-центрично — рекомендация**
  (ключ общий для чата/имперсонации/эмбеддингов; external-прокси остаётся
  env-only); (б) + ключи для external-слотов (по слоту на чат/имп/эмбеддинги —
  усложняет формат ради power-фичи, которой env уже достаточно).
- **Р5. Место хранения.** (а) **`settings.json` — рекомендация** (буква запроса;
  атомарная запись, `.bak`, whitelist бэкапа, downgrade-guard уже работают);
  (б) отдельный `secrets.json` (чуть чище разделение, но новый файл нужно
  проводить через бэкап/миграции/restore, и «конфигурационный файл» из
  постановки — это именно settings).
- **Р6. Записи чужих машин.** (а) **v1 без UI-управления — рекомендация**
  (записей единицы, чистка — правкой файла; задел «забыть другие компьютеры» в
  roadmap); (б) сразу действие в настройках.

## 10. План реализации (после подтверждения развилок)

Два PR (этапы направления, линейно):

1. **`feat/api-key-store` — ядро**: `shared/secrets.rs` (обе схемы + тесты),
   `AppConfig.api_keys` (+serde-тесты), резолюция в супервайзере
   («сохранённый > env», новые тексты статус-чипа), `AppCommand::SetApiKey` +
   шифрование/персист в оркестраторе, round-trip защита, i18n-ключи ошибок.
2. **`feat/api-key-ui` — UI**: режим `mask` у `InputBox`, поле «API-ключ» в
   облачных подсекциях (+эмбеддинги), флаги «настроен» в `AppEvent::Settings`,
   `SettingsIntent::SetApiKey`, описания/i18n, README/spec/CHANGELOG
   (Добавлено + Безопасность).

Документация по итогам: новый ADR «Хранение API-ключей: машинно-привязанное
шифрование в конфиге» + пометка в ADR 0004 (положение «секреты не на диск»
уточняется до «не на диск открытым текстом»), architecture §6/§12, spec (секция
настроек), install.md (env-путь остаётся и документируется как фолбэк).

## 11. Вне объёма / заделы

- OS-кейчейн как дополнительная `scheme` (Windows Hello / Secret Service).
- Мастер-пароль (opt-in «параноидальный» режим) — не обещаем.
- Ключи для external-прокси и env-карт MCP-серверов тем же механизмом.
- UI-управление записями чужих машин («забыть компьютер X»).
- `0600` на `settings.json` при записи (Unix) — можно взять в этап 1 как
  hardening-мелочь.
