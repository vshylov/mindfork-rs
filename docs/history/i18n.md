## 1. Motivation and scope

Today **all** of the application's service text is Russian: background-task system
prompts, tool-schema descriptions, tool-result text, the self-model render scaffold,
role labels in digests, UI chrome. The user-facing part — the profile's system message,
greeting, role names — is already edited per profile.

The problem shows up on a **profile with a non-Russian system prompt**: the model gets
a prompt salad — an English-language persona to which the application mixes in a Russian
"self-model maintenance protocol", Russian descriptions for 30+ tools, and Russian gates
("Similar notes… rewrite via note_revise"). Consequences: leaks of Russian into
replies, worse instruction-following for weaker local models, Russian auto-generated
titles for an English conversation from the "User:/Assistant:" scaffold.

The key distinction the whole plan is built around is **two independent axes**:

- **Axis A — agent language** (text the *model* reads): service prompts, tool
  descriptions/schemas, tool results, injection scaffolding. Determined by the
  **profile** (each agent has its own language) — exactly what the user asked for.
- **Axis B — interface language** (text the *human* reads): status bar, settings
  screen, help, errors, banners. Determined by a **global setting** — one per
  application. Independent of the agent language (user's decision, 2026-07-12): a
  Russian UI with English-speaking agents is a legitimate combination, no inheritance
  between the axes.

The axes intersect in exactly one place: tool results and the self-model are seen by
both the model and the human (tool cards in the feed, the `F3` screen). Principle:
**these texts follow the agent's language** — they are primarily for the model, and a
human running an English-speaking agent expects English in its cards too.

### 2.3 What is deliberately NOT localized

- **Tool ids and JSON field names** — the wire protocol (`note_save`, `content`).
- **The `@self` tag**, config keys, `/rag add|remove|list|rebuild` command names
  (aliases — possible future work, not now).
- **Logs** (`tracing` to file) and **comments/docs** — the "Russian" convention
  (CLAUDE.md) does not change.
- **Data written by the model** (notes, self-model summary/goals/traits, RAG) — lives
  in the language of the conversation; changing the profile language does **not**
  translate them (§6.4).
- **Spellcheck dictionaries** — already multilingual (en_US/en_GB/ru_RU), orthogonal.
- **HTTP client wrappers** (`shared/api/{openai,anthropic,gemini}`) — context around
  network errors: the main payload is the server's error body / an OS string
  (fundamentally untranslatable), and localizing the three or four words of wrapping
  doesn't pay for threading the locale through every client (boundary, see
  docs/history/i18n-cli.md §7). The managed `llama-server` preflight/probe
  (`shared/api/managed.rs`), in contrast, **is localized** — it surfaces in the status
  chip (`ui.err.managed.*`, i18n CLI stage 3).
- **Pre-language contexts** in `shared/paths.rs`/`Paths::resolve` (before the CLI
  language is known — a corrupt `defaults.json`, exe resolution) — stay **English**
  (docs/history/i18n-cli.md §7).

## 3. Proposed architecture

### 3.1 `shared/i18n.rs` — our own micro-module, no new crates

Following the `calc.rs`/ADR 0003 precedent (the project avoids crates when a
home-grown solution is ~150 lines): `rust-i18n` uses a process-global locale (not
per-profile), `fluent-rs` is overkill (pluralization/grammar is needed only by axis B,
not by prompts) and is a foreign DSL. If axis B ends up needing honest pluralization —
revisit separately.

```rust
// shared/i18n.rs (sketch)
pub enum Lang { Ru, En }                    // serde lowercase, Default = Ru
pub struct Locale { lang: Lang, map: HashMap<String, String> }
impl Locale {
    pub fn t(&self, key: &str) -> &str;                    // with fallback: ru → the key itself
    pub fn tf(&self, key: &str, args: &[(&str, &str)]) -> String; // {name} substitution
}
pub fn locale(lang: Lang) -> &'static Locale;  // LazyLock table of built-in bundles
```

- Bundles — `locales/ru.json`, `locales/en.json` in the repo, `include_str!` + parsed
  on first access (`LazyLock`). A missing key **never panics**: falls back to `ru`
  (the reference language), then to the key itself.
- Placeholders — named `{name}`, simple substitution (no plural rules: the existing
  wording is already number-neutral — "×{n}", "notes: {n}").
- External files (`data/locales/*.json`, override/new languages without a rebuild) —
  Tier 3: loaded at startup on top of the built-ins (`Box::leak` — the syntect-theme
  cache in `markdown/code.rs` is the precedent).

**File format — JSON** (project convention + user's request). JSON's drawback for long
prompts is `\n` escaping; solved by a **string-array** value
(`["line 1", "line 2"]` → `join("\n")` on load) — readable and still plain JSON.

### 3.2 Profile language: chosen at creation, locked once data exists

**User's decision (2026-07-12).** Rationale: the self-model, the interlocutor model,
notes and the rest of a profile's memory are all written in one language — so the
language is chosen **when the profile is created**, and changing it is **forbidden**
once the profile has data. This constraint deliberately simplifies the
implementation: mixing languages within one profile's data becomes impossible by
construction.

- `Profile.language: Lang` — a **concrete value, not `Option`** (`#[serde(default)]`
  → every existing profile reads as `Ru`, which is correct: their data is Russian).
- **There is no global agent language.** The idea of an `Option<Lang>` fallback to
  `AppConfig.language` from the first version of the plan is **rejected**: the profile
  language is not tied to the UI language (axis B, future). The interface-language
  setting arrives with axis B and does not affect profiles.
- **Chosen at creation**: `Ctrl+N` in settings creates a profile instantly (no dialog),
  so "chosen at creation" is implemented as: a new profile inherits the language of
  the profile selected in settings at creation time (fallback `Ru`; the first-run
  bootstrap profile — `Ru`), and the "Language" field in the Persona subsection is
  **editable as long as the profile has no data** — you can set it as the first action
  after creation.
- **Lock**: the predicate "data exists" = the profile's visible chats > 0 **OR** the
  self-model is non-empty **OR** active notes (including `@self`) > 0. RAG documents
  are deliberately excluded from the predicate: the language of knowledge-base files
  is set by the user, not the agent. A double gate: (1) the settings field renders
  locked with a reason hint (the "honest gate" pattern from tool toggles,
  `FieldRow.warn`); the `AppEvent::Settings` snapshot gains a set
  `language_locked: Vec<Uuid>` (computed by the orchestrator — the screen has no
  access to chats/DB); (2) an authoritative check on `UpdateProfile` in the
  orchestrator — an attempted change while data exists is rejected with a clear error
  (a safety net against the snapshot going stale).
- **Consequence**: a chat's language = its profile's language **forever** (a profile
  with chats cannot change language) — resolution is trivial, "switching language
  mid-chat" doesn't exist as a scenario. Imported (`import-lamellama`) profiles get
  `Ru` via serde-default — correct for existing data.
- **Default language — from `defaults.json`** (not hardcoded `Ru`): the install-time
  file next to the binary (`shared::paths::Defaults`) carries `default_language`, which
  is used to create the **first** (bootstrap) profile and new profiles
  (`CreateProfile`). The installer will fill it in based on the language chosen at
  install time — so the first profile is created directly in the right language.
  Resolution: `Paths::default_language()` → `OrchestratorDeps` →
  `Orchestrator::default_language`. See [docs/install.md §2.1](../install.md).
- **Bootstrap nuance**: the first profile is created **together with the default
  chat** → immediately locked to its language (its language can no longer be
  changed). That's why the language is chosen at install time (`defaults.json`), not
  edited afterward. For an agent in a **different** language than the install-time
  one, create a **new** profile (a fresh one has no data → the language is editable)
  and set the language before the first chat.
- Unlocking is honest: hide (soft-delete) all chats and the data is empty → the
  language is editable again — there's nothing left for it to contradict.

### 3.3 Wiring (which signatures get touched)

| Consumer | How it gets the language |
|---|---|
| Background tasks (title / impersonation / reflection / consolidation) | the orchestrator resolves it from the chat's profile at spawn time, passes `&'static Locale` into the task's parameters |
| Agentic loop and tools | `TurnInfo.lang` → `ToolContext.loc` (a snapshot for the turn; `ToolContext::new` is the single point of change, SOLID stage 1) |
| Tool schemas | `ToolRegistry::schemas_for(enabled, loc)` → `Tool::schema(loc)` → `description(loc)`/`parameters(loc)` — a mechanical trait-signature change (35 impls); schemas are already built on every request, no cache — nothing breaks |
| `entities` (self-model rendering) | `render_for_prompt`/`render_full`/`age_label` take `&Locale` as a parameter (FSD allows it: `entities → shared`; precedent — the `recent` parameter ripple in narrative-as-notes) |
| The `F3` screen | **not affected**: it renders its own section labels ("About yourself:", "Interlocutor", "Observations" in `screens/self_model.rs`), not `render_full` — this is UI chrome, axis B; the model's actual data stays in the agent's language |
| `inject_self_model` | +`loc` parameter (a pure, testable function) |

Catalog metadata for the UI (`ui_label()`, `ToolGroup::title()`) is **axis B** and is
not touched in this track.

### 3.4 Bundle key structure

Dotted namespaces: `prompt.title.system`, `prompt.impersonation.default`,
`selfmodel.policy_core`, `selfmodel.render.header`, `selfmodel.age.today`,
`tool.note_save.desc`, `tool.note_save.param.content`, `tool.note_save.gate.similar`,
`digest.role.user`, `defaults.system_message`, `defaults.profile_name`. The `ui.*`
namespace is reserved for axis B (same mechanism).

### 3.5 Tests: expectations from the bundle + run against every locale

**User's decision (2026-07-12).** Expected service-text values in tests are **not
duplicated as literals** — they're pulled from the same bundle the code uses; tests
covering localized text **run against every built-in locale** — so per-language
problems get caught by the unit suite, not by a live run. (The first version of the
plan proposed the opposite — "byte-exact ru bundle + literals in tests for zero
churn"; rejected in favor of per-language coverage.)

- **Mechanism — no new crates, no global state**: the locale is already passed
  per-call (`&Locale`), so "run against every translation file" is a
  `for lang in Lang::ALL { … }` loop inside the test (testkit fixtures take the
  language as a parameter); failure messages include the language.
  No separate CI matrix is needed.
- **What per-language coverage catches**: unfilled/extra `{placeholders}`; broken
  cross-references (§6.2) — a prompt and the block generator take a heading from the
  same key, and consistency is checked in every language; the effect of
  **translation length** on character budgets (`render_for_prompt`: the en text has a
  different length — truncation and per-section budgets must line up in every
  locale); compatibility of `parse_console` with localized labels.
- **Boundary of what moves out**: expectations for **service** text move into the
  bundle; test data/fixtures (user messages like "how are you?", names, note
  content) stay as literals — that's data, not translation.
- **Tautology caveat**: comparing "output == the bundle value" doesn't catch
  corruption of the wording itself (the bundle is compared against itself). For
  hard-won phrasing we keep **meaning pins** — small per-language tables of key
  phrases right in the tests (ru: "точность важнее угодливости", "СОКРАЩАЙ"; en: their
  equivalents), like today's `POLICY_CORE.contains("СОКРАЩАЙ")`, but for every
  language.
- **Completeness gate tests** stay: the key sets of all built-in locales match; the
  `{placeholder}` set for each key matches across languages.
- **Live smokes (`#[ignore]`) are not looped over locales** (expensive): the ru suite
  stays as is, en mirrors of key scenarios are added in Tiers 1–2 with the criterion
  "no Cyrillic in the prompt/results".
- **External locale files** (Tier 3) are not covered by unit tests (user content) — at
  load time a log warning about missing keys + fallback.
- **Cost**: rewriting hundreds of assertion sites to bundle keys is noticeably more
  churn than the first version of the plan; an accepted cost for per-language
  coverage. Mechanical but careful in places with placeholders (assert via `tf` with
  the same arguments, or by a constant key fragment); done group by group along with
  the tiers (tier's text → tier's keys + tests).

## 4. Decision points (confirm before implementation)

1. **Scope of this track.** (a) Now — only axis A (agent language: prompts +
   tools), axis B (UI) — a separate track later; (b) both axes at once.
   **User's decision (2026-07-12): (a).** The mechanism (`shared/i18n`, bundles) is
   designed to be shared — axis B will reuse it later via `ui.*` keys.

2. **Language distribution model.** ~~(a) `Option<Lang>` + a global default; (b)
   global only~~ — **user's decision (2026-07-12), replaces both alternatives**: the
   language is chosen at profile creation, stored as a concrete
   `Profile.language: Lang` value, **locked** once data exists (chats /
   self-model / notes), and **not tied** to the UI language. Details and the lock
   predicate — §3.2.

3. **Bundle storage.** (a) external `data/locales/*.json` only; (b) built into the
   binary only (`include_str!` from the repo's `locales/`); (c) hybrid — built-in
   ru+en + external overrides/additional languages. **User's decision (2026-07-12):
   (b) for Tiers 1–2, (c) — Tier 3.** Built-ins have no "file not found/stale" failure
   mode (critical: prompts are functionality, not decoration); external files add a
   bonus — tuning service prompts without a rebuild, but need versioning. Clarifying
   the original brief: "a separate json file per language" is satisfied in both
   variants — the only question is whether it's read from the repo at build time or
   from disk at startup.

4. **Tool descriptions/schemas.** (a) localized by profile language (from the
   bundle); (b) one language for everyone — English (the LLM lingua franca, industry
   standard). **User's decision (2026-07-12): (a)** — today's ru-profile behavior
   (descriptions battle-tested by live smokes on Gemma) is preserved byte-for-byte,
   and the infrastructure is being built for tool results anyway — the extra cost is
   just the volume of translation (~100 keys).

5. **Starting language set.** **User's decision (2026-07-12): ru + en.** The agent
   does the en translation; wording review is the user's call (critical for
   "hard-won" texts: `POLICY_CORE`, gates, "accuracy over flattery"). More languages —
   "just another JSON" in Tier 3.

6. **The model's reply language.** **User's decision (2026-07-12): confirmed as a
   principle.** The profile language controls **only** the service scaffold; the
   application does **not** impose an "answer in language X" instruction — that lives
   in the profile's user-authored system message, or nowhere. Rationale: the reply
   language need not match the scaffold language — e.g. a profile for learning a
   foreign language (scaffold in the native language, replies in the target
   language). `TITLE_SYSTEM_MESSAGE` already asks for a title "in the language of the
   conversation" (not "in the profile's language") — that behavior is preserved in
   both bundles.

7. **Defaults for new entities.** A new profile gets `DEFAULT_SYSTEM_MESSAGE`, the
   name "Assistant", `CharacterNames` and the title "New chat" **in the profile's
   language** (a snapshot — it's data, edited normally afterward). Existing
   profiles/chats are untouched. **Settled** by decision point 2 (the language is
   chosen at creation — defaults are created in it); nuance: editing the language
   before the first chat (while the lock is still open) regenerates the default
   `CharacterNames`/system message only if the user hasn't already edited them
   (otherwise leave them alone — it's already the user's data).

## 6. Risks and pitfalls ("harder than it looks")

1. **Test churn — large and accepted.** Hundreds of assertions on Russian substrings
   move to bundle keys + a per-locale loop (user's decision, §3.5). Mitigations: the
   work goes group by group along with the tiers (not one giant PR); the ru bundle is
   extracted from the current strings **verbatim** anyway (ru-profile behavior
   doesn't change, live smokes stay green); meaning pins for key phrases guard
   against the "the bundle is compared against itself" tautology.
2. **Text cross-references.** Prompts reference headings generated by other
   functions: `reflect_system_message` ↔ "Consolidation overview for observations"
   (`overview.rs`) and "Behavior signals" (`behavior_markers`); the `note_link`
   description ↔ "id from note_recall"; `present.rs::parse_console` **parses**
   `python::format_output`'s output by labels ("exit code:") — localizing the labels
   without touching the parser would break the console card. Needs a registry of
   these links + gate tests for in-language consistency (§3.5).
3. **Dynamic text.** `python_exec` descriptions (mode/network/packages) and
   `get/set_sampling` (scope_note by provider) are assembled with `format!` — in the
   bundle these become keyed fragments with arguments, composition stays in code
   (like `maintenance_protocol()` wrapping `POLICY_CORE`).
4. **Mixed languages in data — mostly prevented by the lock.** Changing a profile's
   language once it has data is forbidden (§3.2), so "Russian notes inside an English
   scaffold" within one profile is impossible by construction. Residual cases: (a)
   Tier 1 without Tier 2 = en prompts + ru tools — a temporary, deliberate state; (b)
   the user writes to the agent in a language other than the profile's — the scaffold
   stays the profile's language (correct: the profile language is the agent's
   contract, not auto-detection).
5. **Quality of the en prompt translations.** The wording was shaped by live tests
   (anti-flattery, gates, "integrate and SHORTEN") — the translation must preserve
   the force of those nuances; user review + en smokes are mandatory (decision
   point 5).
6. **Prefix cache.** Changing the profile language changes the system message → one
   context re-process; a rare operation, an accepted cost (precedent — the
   self-model injection, decision 2026-07-03).
7. **`&'static Locale` vs. external files.** Built-in bundles give `&'static` for
   free; external ones (Tier 3) — `Box::leak` at startup (finitely many languages,
   precedent — the syntect-theme cache). Don't start with `Arc` — no premature
   signature complexity.

## 7. Out of scope

RTL languages (terminals aren't ready), honest pluralization/grammar (needed only by
axis B — decide there), auto-translation of existing data, localization of
logs/comments, `/rag`-command aliases, translation of the project's documentation.
